# Policy Creation

Create OPA policies from natural language specifications. The agent follows `opa_policy/policy_creation/opa_policy_creation.md` to generate a `.rego` policy file.

## Inputs

Located in `<TARGET_AGENT_PATH>/smith/`:

- `guidance.txt` — natural language policy rules
- `tool_definitions.json` — MCP tool list with parameters (auto-generated by `smith --flag get_mcp_parameter`), maps to `input.arguments.*`
- `system_vars.json` — system/session variables (e.g., roles, teams), maps to `input.extensions.subject.*`
- `test_case_template.json` (in `./references/`) — defines the OPA input envelope structure

## Output

OPA policy saved to `<TARGET_AGENT_PATH>/smith/policy_generated.rego`

## How It Works

Smith turns natural-language guidance into a validated `.rego` policy in a few clear steps:

1. **Extract tool definitions.** `smith --flag get_mcp_parameter` connects to the running MCP server and writes `tool_definitions.json` (tool names, parameters, types). These parameters become `input.arguments.*` in the policy.

2. **Analyze the guidance first.** Each rule in `guidance.txt` is mapped to a tool and checked for enforceability: *can this rule be expressed using only the tool's arguments (`input.arguments.*`) and the system variables (`input.extensions.subject.*`)* Rules that need data available in neither are **not** guessed at — they are set aside (see step 5). Smith asks for your confirmation before generating.

3. **Generate the policy.** Each enforceable guidance rule becomes one `deny` block with a clear message, wrapped in a `default allow := false` / final `allow` structure (`package mcp.policies`). Every deny rule traces back to a specific guidance line — Smith does not invent rules. Output goes to `<TARGET_AGENT_PATH>/smith/policy_generated.rego`.

4. **Validate and auto-fix.** The generated policy is compiled with `smith --flag policy_validation`. If it doesn't compile or has formatting issues, `smith --flag policy_validation_fix` auto-fixes and re-validates until it's clean (LLM will be involved in validation steps if necessary). A policy is never presented until it compiles.

5. **Log what couldn't be enforced.** Any guidance rule requiring context not in the tool arguments or system variables is written to `extension_suggestions.json` as an informational suggestion — it is **not** added to the policy.

6. **Human approval → move policy.** Smith presents the generated policy for review. Nothing is applied automatically: only after you approve is the policy moved into place (`assets/opa/policy.rego`) to become the policy under management. If you're not satisfied, you give feedback and it regenerates.

The guiding constraint throughout: the policy may **only** reference data available from tool arguments or system variables — never hypothetical or invented fields.

## CLI Usage

The agent runs these stages for you when you ask it to create a policy; you can also invoke them directly:

```bash
# Auto-extract MCP tool definitions (connects to the running MCP server)
smith --flag get_mcp_parameter

# Validate a generated policy compiles
smith --flag policy_validation --policy_path <TARGET_AGENT_PATH>/smith/policy_generated.rego

# Validate and auto-fix formatting
smith --flag policy_validation_fix --policy_path <TARGET_AGENT_PATH>/smith/policy_generated.rego
```
