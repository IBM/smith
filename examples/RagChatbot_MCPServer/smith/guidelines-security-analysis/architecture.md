### Prompt Inputs

| Field or data | Source | Consumer | Trust / influence |
|---|---|---|---|
| user chat message (question) | Streamlit st.chat_input(), i.e. direct end-user text. | enforce_input() LLMGuard scan, then embedded into the 'user' role message sent to the LLM as 'Current task/question: ' + question. | Untrusted; scanned for prompt injection/PII/toxicity, but a hardcoded business-safe-word allowlist can override a scanner block, and if no malicious-pattern match is found the text is still allowed through with only a warning even when LLMGuard itself flagged it. |

| memory_text (prior turns, up to last 10 messages) | st.session_state.messages, built from prior user/assistant turns in the same Streamlit session. | Appended into the system prompt as conversation history for the LLM. | Mixed trust: includes prior user input (untrusted) and prior assistant/tool output (which may include real HR data if a compensation tool was called earlier in the session), re-fed into later prompts without re-scanning through enforce_input. |

| tool output text (e.g. compensation JSON/CSV, email confirmations) | Each MCP tool's return string. | Appended as a 'role: tool' message back into the LLM conversation for the next turn, after enforce_output(); also directly surfaced to the user once the LLM stops calling tools. | Treated as at least partly trusted (fed back into the LLM as ground truth); enforce_output applies PII/substring redaction, but denial messages beginning with the specific emoji marker bypass all output scanning. |

## Enforcement Points

| Layer | Current | Available (OPA-interceptable) | Blind spots |
|---|---|---|---|
| Prompt/LLM input (Streamlit client) | enforce_input(): LLMGuard PromptInjection/Anonymize/BanSubstrings/Secrets/Toxicity/Language scan, with a business-safe-word allowlist that can override a scanner block and a narrow hardcoded malicious-substring list that is the only thing that actually raises a blocking exception. | Not directly OPA-interceptable as implemented (free-text heuristics, not structured input.args/subject fields); an OPA decision could still gate whether a request reaches the LLM at all if the client called out to OPA before invoking the model, but no such call exists today. | The business-safe-word allowlist can let a flagged prompt-injection attempt through if it also contains an allowlisted business word; conversation memory (memory_text) is re-injected into later prompts without being re-scanned. |
| MCP tool dispatch (mcp_server.py) | None: no decorator, middleware, or explicit call to opa_client.evaluate_policy wraps any active @mcp.tool() function. | Yes -- this is the natural pre-execution point: input.args.* for every tool (department, select_fields, external_sharing, destination, amount, format, export_type, etc.) is fully declared in tool_definitions.json and available at the moment each tool function is entered, so a Rego decision keyed on tool name + declared arguments could gate every tool call before business logic runs. | None structural at this layer for argument-based checks; the blind spot is that role/identity (input.extensions.subject.*) is not reliably available here (see Runtime Subject Context) because it is self-asserted and not verified, so any future policy gating tool arguments would still need a trustworthy subject source to enforce role-based rules like guidance rules 1-2, 4-5, 9-10. |
| Runtime subject/identity (opa_client.current_user_context) | In-process mutable dict updated by whichever caller invokes set_user_context; no authentication step observed anywhere in the inspected tree. | The shape needed (extensions.subject.id/roles/teams/permissions) is already defined in UniversalOPAClient.get_principal_context()/build_universal_input(), so once wired, role-based decisions are OPA-expressible; the field values would be exactly as trustworthy as their current provenance, which is client-self-asserted with no verification mechanism documented anywhere in this tree. | True blind spot: there is no identity/authentication layer in this codebase. Any OPA policy keyed on input.extensions.subject.roles would be enforcing a client-asserted claim, not a verified one, unless an integrity mechanism is added upstream (out of scope for this guidance-only phase to invent). |
| External OPA policy server | Fully implemented client (OPAClient.evaluate_policy, UniversalOPAClient) with a documented fail-secure fallback (_fail_secure_decision) for role/domain/external-sharing/time-range/sensitive-field checks, but zero call sites from any active tool in mcp_server.py. | Yes in principle -- this is precisely the pre-execution OPA hook the rest of the system was designed around; it is simply unconnected to the live tool-call path in this snapshot of the code. | None structural; the gap is wiring, not expressibility. Recorded as a gap for downstream phases, not invented as an enforcement point that exists today. |
| Tool response / output (Streamlit client) | enforce_output(): LLMGuard Sensitive/BanSubstrings(example literals)/Toxicity/Relevance/NoRefusal scan on every tool result and final assistant message, except messages starting with the deny-emoji marker, which bypass scanning entirely. | Not OPA-interceptable as a pre-execution decision (it runs after the tool already executed and returned real data); it is a post-hoc mitigation, not a substitute for pre-execution argument/subject-based gating. | By the time this runs, view_team_compensation/export_compensation_data have already assembled and returned full sensitive records into the tool-result string; BanSubstrings only catches the specific example literal values hardcoded in llm_guard_config.py (e.g. two example SSNs/addresses/bank-account suffixes), not the full range of fixture records in data_sources/hr_database.py, so most real sensitive values in this dataset would not be redacted by the literal-substring list. |

## Phase Handoff

- Status: PASS
- Artifact schema: architecture-v2
- Summary: Analyzed examples/RagChatbot_MCPServer: 10 registered MCP tools over SSE (mcp_server.py), all with an implementation finding (no Unknowns) cross-checked against tool_definitions.json with no name/signature mismatches. Layers identified: Streamlit agent/client with LLMGuard prompt/output scanning, MCP transport/dispatch with zero pre-execution checks, tool implementations backed by static in-memory HR/compensation/purchase fixtures, a fully-built but entirely unwired OPA client/schema-transform layer (opa_client.py), and an external OPA server that is never called from any live tool path. 3 runtime-subject fields recorded, all self-asserted client-side with no authentication or integrity mechanism, and none currently reach any OPA-visible field via an active code path; system_vars.json itself was not found to be loaded by any inspected file. 31 tool-argument rows recorded across all 10 tools; several required arguments material to guidance (department and id on both compensation tools, report_data, external_sharing across two tools, amount's relation to budget limits, category/justification on purchase) are implementation-Ignored or merely Echoed rather than Acted on, meaning the described behavior in tool docstrings/guidance does not match what the code does. 4 undeclared-field gaps recorded, the most significant being that no trustworthy, declared field currently identifies requester role/team for any role-conditioned guidance rule (1,2,3,4,5,6,9,10,16), and that view_team_compensation/export_compensation_data ignore their own department/id arguments and instead always return a hardcoded manager's team. Enforcement points: the OPA-interceptable pre-execution hook at MCP tool dispatch is structurally available (all tool arguments are declared and present at that point) but currently has zero enforcement; the only active controls are prompt-layer LLMGuard scans (input allowlist can override a block; output scan skips deny-marker messages and only redacts a short hardcoded list of example literal values, not the full fixture dataset). Open gaps for Phase B: reconcile system_vars.json's declared role vocabulary/loading with the runtime code's actual (self-asserted, unauthenticated) role source; treat department/id arguments on the two compensation tools as currently non-functional for scoping; note the unresolved llm_guard_copy import and the unresolved set_user_role tool call as Unknown, not proven-missing, per the shared analysis rules.
