## Threat Model Skill

Applies the OWASP Top 10 for LLM Applications 2025 to a target MCP server
and produces `threat_model.md`. Requires `architecture.md` and
`policy_guidance_questionnaire.md` to be present in the target directory.

### Authoritative Paths

- Input 1: `<mcp_server_dir>/policy_generation/architecture.md` (from architecture_analysis skill)
- Input 2: `<mcp_server_dir>/policy_generation/policy_guidance_questionnaire.md`
- Output: `<mcp_server_dir>/policy_generation/threat_model.md`

### Workflow (follow strictly)

---

#### STEP 1 — Read inputs

Read both input files in full before proceeding.
If either file is missing, stop and tell the user which file is needed.

---

#### STEP 2 — Apply OWASP LLM Top 10

Evaluate each category below IN ORDER against this specific tool.
For each category follow the three-question test:

1. **Does the attack surface exist for this tool?**
   Base this on `architecture.md` — what inputs does the tool accept,
   what external systems does it call, what data flows through it.

2. **Is there a specific threat instance for this tool?**
   A threat instance is concrete: it names the specific field, layer,
   or behaviour that is at risk. Generic statements ("the LLM could
   be manipulated") are not threat instances.

3. **What is the evidence from the tool's design?**
   Cite specific fields, files, or behaviours from the input documents.

---

**LLM01 — Prompt Injection**
*OWASP definition:* A Prompt Injection vulnerability occurs when user prompts alter the LLM's behavior or output in unintended ways. These inputs can affect the model even when imperceptible to humans.
Attack surface: free-text inputs that reach the tool's parameters or
that are returned by external services and fed back to the agent.

Questions to ask:
- Which parameters accept free-text strings? (check questionnaire Section 1, Q4)
- Are any parameter values passed to an external service without sanitisation?
  (check architecture.md Tool Implementation layer)
- Does the tool return text from an external source that the agent
  processes further?

---

**LLM02 — Sensitive Information Disclosure**
*OWASP definition:* LLMs, especially when embedded in applications, risk exposing sensitive data, proprietary algorithms, or confidential details through their output.
Attack surface: data returned to callers who should not have it, or
credentials/context embedded in the system prompt.

Questions to ask:
- What fields does the tool return? Could any be sensitive?
  (check questionnaire Section 6)
- Are session variables or system context injected into the agent's
  system prompt in a way they could be extracted? (check architecture.md
  Agent layer)
- Is access gated by a role that is self-reported?
  (check architecture.md Trust Boundaries)

---

**LLM03 — Supply Chain**
*OWASP definition:* LLM supply chains are susceptible to various vulnerabilities that can affect the integrity of training data, models, and deployment platforms.
Attack surface: external libraries, upstream APIs, and data sources
the tool depends on.

Questions to ask:
- What external services does the tool call?
  (check architecture.md External Service layer)
- Is the response from the external service parsed and returned
  without validation?
- Are dependencies pinned?

---

**LLM04 — Data and Model Poisoning**
*OWASP definition:* Data poisoning occurs when pre-training, fine-tuning, or embedding data is manipulated to introduce vulnerabilities, backdoors, or biases that compromise model security, effectiveness, or ethical behavior.
Attack surface: untrusted inputs that shape policy decisions or
model reasoning.

Questions to ask:
- Are any identity or role fields self-reported?
  (check architecture.md Trust Boundaries, classification = Self-reported)
- If a caller falsifies a self-reported field, what additional access
  do they gain?

---

**LLM05 — Improper Output Handling**
*OWASP definition:* Improper Output Handling refers specifically to insufficient validation, sanitization, and handling of outputs generated by large language models before they reach downstream systems. Since LLM-generated content can be shaped by prompt input, this effectively grants users indirect access to additional functionality.
Attack surface: tool output that is returned unsanitised to downstream
consumers (agent, browser, database).

Questions to ask:
- Does the tool parse and return raw external content (HTML, JSON)?
- Is that content validated or sanitised before being passed to the agent?
  (check architecture.md Tool Implementation layer current enforcement)

---

**LLM06 — Excessive Agency**
*OWASP definition:* Excessive Agency occurs when an LLM-based system is granted more capability, permissions, or autonomy than is necessary to complete its intended task, enabling harmful actions when the model is manipulated or makes mistakes.
Attack surface: the tool being invoked beyond its stated scope —
wrong callers, excessive data volumes, unrestricted parameter values.

Questions to ask:
- Are there role-based restrictions on what the tool can be asked to do?
  (check questionnaire Section 3)
- Are there numeric caps on parameters?
  (check questionnaire Section 4)
- Are there session-level rate limits?
  (check questionnaire Section 5)
- What is the worst case if all restrictions are removed?

---

**LLM07 — System Prompt Leakage**
*OWASP definition:* The system prompt leakage vulnerability in LLMs refers to the risk that system prompts or instructions used to steer model behavior can inadvertently reveal confidential or proprietary information to users.
Attack surface: system prompt content (including policy constraints,
session variables, role instructions) that can be extracted by the user.

Questions to ask:
- Are session or policy variables injected directly into the system prompt
  as plain text? (check architecture.md Agent layer)
- If a user asks "what are your instructions?", what could the LLM reveal?

---

**LLM08 — Vector and Embedding Weaknesses**
*OWASP definition:* Vectors and embeddings vulnerabilities present significant security risks in systems utilizing Retrieval Augmented Generation (RAG). Weaknesses in how these elements are generated, stored, or retrieved can be exploited to inject harmful content, manipulate outputs, or expose sensitive data.
Attack surface: RAG pipelines, vector stores, embedding models.

Question to ask:
- Does this tool use retrieval-augmented generation, vector search,
  or embedding-based lookup? (check architecture.md, tool source files)
- If no: mark as NOT APPLICABLE.

---

**LLM09 — Misinformation**
*OWASP definition:* Misinformation occurs when LLMs produce false or misleading information that appears credible. This vulnerability can lead to security breaches, reputational damage, and legal liability.
Attack surface: the LLM generating plausible but factually incorrect
responses based on the tool's output.

Questions to ask:
- Does the tool return factual, structured data or free-form text?
- Does the agent make safety or access decisions based on this data,
  or only present it to the user?

---

**LLM10 — Unbounded Consumption**
*OWASP definition:* Unbounded Consumption occurs when an LLM application permits excessive and uncontrolled inferences, creating risks of denial of service, economic loss, model theft, and service degradation — particularly in resource-intensive cloud environments.
Attack surface: unlimited calls to external services, unlimited data
volumes per call, no session-level rate limiting.

Questions to ask:
- How many external HTTP/API calls does one tool invocation make?
  (check architecture.md External Service layer)
- Is there a cap on result volume per call? (check questionnaire Section 4)
- Is there a session-level call limit? (check questionnaire Section 5)
- What happens if both are absent?

---

#### STEP 3 — Write threat_model.md

Write the output file to `<mcp_server_dir>/policy_generation/threat_model.md` using exactly
this structure for each OWASP category:

```
# Threat Model: <tool-name>

## LLM01 — Prompt Injection
**Applicable:** Yes / Partial / No
**Evidence:** <cite specific field, file, or behaviour>
**Threat instances:**
- <specific, concrete threat with field name and attack vector>
- [add only if a distinct second instance exists]
**Not covered:** <aspects of this category that do not apply to this tool>

[repeat for LLM02 through LLM10]
```

Rules for writing threat instances:
- Every threat instance must name a specific field or layer
- Do not write generic LLM risk statements
- If a category is Not Applicable, write one sentence explaining why
- Partial means some sub-risks apply and some do not — split them explicitly

---

#### STEP 4 — Human review

Present a summary table:

| Category | Applicable | # Threat instances |
|---|---|---|
| LLM01 | Yes/Partial/No | N |
...

Log the summary table and continue automatically to the enforcement_mapping skill.
